# 粉笔 CLI 刷题工具：技术方案选型

我的建议是：采用「终端 TUI + 独立题库适配层」的架构，优先用 TypeScript + Ink 实现，而不是网页套壳，也不建议直接改造整个 VS Code 插件。

对于粉笔题库接入，可以先利用 `maoguy/fenbi-client` 和 `Jolly-Xu/fenbi` 中已有的接口代码做兼容性研究，但要注意：这些属于非公开接口，未经授权不能默认将它们作为长期稳定的数据来源。

## 一、三种接入方案对比

| 维度      | 直接调用粉笔 API    | Playwright 浏览器自动化 | 网页套壳      |
| ------- | ------------- | ----------------- | --------- |
| 真正的终端刷题 | &#x20;最适合     | &#x20;可实现         | &#x20;不适合 |
| 资源消耗    | 低             | 较高                | 中等        |
| 请求速度    | 通常较快          | 受浏览器影响            | 取决于官网     |
| 登录处理    | 需管理认证会话       | 浏览器正常登录           | 官网正常登录    |
| 开发复杂度   | 中             | 高                 | 低         |
| 网站改版影响  | API 变更影响大     | DOM 变化影响大         | 通常较小      |
| 长期维护    | 中高            | 高                 | 低         |
| 适用场景    | 交互式 CLI / TUI | 自动化测试、辅助操作        | 桌面应用      |

这是技术适配性比较，不代表粉笔已经授权第三方接口或自动化访问。

### 为什么更倾向 API 路线？

我重新核查了两个 GitHub 项目的源码。它们已经实现了一条比较完整的刷题链路：

获取题目分类

创建专项练习

读取题目和选项

逐题提交答案

提交练习、读取解析

这些步骤均有对应的网络请求函数，因此你不需要从零研究练习业务流程。

但源码存在 ≠ 当前接口可用。项目里的请求参数仍有 `version=3.0.0.0`，我尚未验证这些接口在 2026 年是否仍能正常完成整套练习。

另外，粉笔用户协议对其题库内容和非授权使用有限制，因此开发时应先确认使用权限；如果计划公开发布，最好获得平台授权。

## 五、我建议先验证两个问题，再投入开发

第一：旧版粉笔 API 是否仍然可用。

重点验证创建练习、获取题目、提交答案、获取解析这四个操作能否组成闭环。需要使用有权访问的账号及接口，不应绕过登录验证或其他平台保护措施。

第二：接口返回的题目格式是否适合终端。

重点检查题干中是否包含 HTML、图片、数学公式、表格，以及多题共用材料的场景。这决定了 CLI 能否覆盖你实际需要的题型。

我建议分两阶段实施：先用本地测试题库完成 Ink 版 TUI，再在确认粉笔授权及接口兼容性后接入真实题库。这样即使粉笔接口失效，整个 CLI 工具也不会被迫重做。

如果目标是做一个像 Codex CLI 一样、在终端内可以长期使用的刷题工具，我会选这条路线，而不是把 Playwright 当作主要刷题引擎。
